# AGENTS.md — Инструкция для ИИ-агентов (PWDTT Split Tunneling)

## 1. Быстрый старт новой сессии (минимальный контекст)

НЕ загружай весь репозиторий в контекст. Для начала работы прочитай **только 3 файла**:
1. `AGENTS.md` (этот файл)
2. `docs/STATUS.md` (текущая активная задача и список нужных файлов)
3. Паспорт целевого модуля из `docs/modules/<module>.md`

При необходимости проверь релевантный ADR в `docs/DECISIONS/`.

## 2. Неизменяемые архитектурные инварианты

- **Целевая ОС:** Windows 11 (x64). Кроссплатформенные сборки Linux/macOS НЕ должны ломаться — используй `//go:build windows` и `service_stub.go`.
- **Драйверная модель:** Без подписи собственного kernel-драйвера. Маршрутизация: WinDivert 2.2 (подписанный WHQL `WinDivert64.sys`) + user-mode WFP Kill Switch.
- **Независимость от upstream (`luminescq/PWDTT`):**
  - Весь новый Go-код — строго в `internal/splittunnel/`.
  - Весь новый UI-код — строго в `frontend/src/splittunnel/`.
  - Настройки — строго в отдельном `split_tunnel.json`.
  - Не дублируй WireGuard/Wintun и не изменяй логику VK TURN/DTLS.
  - Изменения файлов upstream допускаются только в 4 согласованных швах (`wg_windows_init.go`, `app.go`, `main.go`, `frontend/src/App.tsx`).
- **Безопасность:** Kill Switch включён в режиме `fail-closed` по умолчанию. Запрещено запускать деструктивные тесты WFP/WinDivert на основной системе разработчика — только в изолированной VM.

## 3. Десять обязательных правил выполнения задач

1. Выполняй **только одну** согласованную подзадачу из `docs/ROADMAP.md` за раз.
2. Перед правкой читай только файлы, перечисленные в `docs/STATUS.md` и паспорте модуля.
3. Не переписывай существующие файлы целиком — вноси точечные минимальные правки.
4. Не изменяй несвязанные модули и код upstream вне области текущей задачи.
5. Не добавляй внешние зависимости в `go.mod` или `package.json` без фиксации причины в ADR.
6. Не удаляй и не ухудшай существующий функционал PWDTT (Global-режим должен работать 1:1 с оригиналом).
7. Не переходи к следующей подзадаче, пока текущая не прошла свои unit/интеграционные тесты.
8. При обнаружении архитектурного противоречия остановись, объясни проблему и предложи корректировку плана/ADR до правки кода.
9. Фиксируй завершённую подзадачу отдельным коммитом: `split-tunnel(<module>): <summary>`.
10. В конце каждой задачи обязательно обнови `docs/STATUS.md`, `docs/CHANGELOG.md` и (если менялись интерфейсы) паспорт модуля в `docs/modules/`.
